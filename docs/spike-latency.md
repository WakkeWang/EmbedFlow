## 为什么这条是承重墙

expect 匹配器在服务端（决策 4A/6A）的前提是：uboot 阶段的紧时序窗口能容忍
「设备 → COM → 客户端 → WS → 服务端匹配器 → 回发」的往返延迟。若不能，
匹配器必须下沉进 serial-client。这是全计划唯一可能迫使服务端返工的未知数。

## 预算（来自 VBS 脚本的时序特征）

| 阶段 | 典型窗口 | 预算上限（含余量） |
|---|---|---|
| uboot 密码提示后输密码 | 秒级（人工/脚本发送前有完整提示等待） | 往返 < 500ms 完全安全 |
| `<board>#` 提示符 → 发 boot 命令 | 秒级 | 同上 |
| 逐字符回显类交互（最坏情况） | 无硬窗口，但操作员观感 | 往返 < 200ms 无感 |

结论先行：**115200 波特下，一帧 8 字节约 0.7ms 线路时间；WS 局域网往返
通常 1-10ms。理论上限远低于预算。** spike 的目的是用实测数字关闭这个假设，
而不是靠理论。

## 工具（已实现，随仓库分发）

### 服务端

```bash
# probe 模式：纯 echo，无 store/会话/日志，测出的就是隧道裸延迟
./embedflow-server -probe-echo -addr :8420
```

### 客户端（serial-client）

```powershell
# 模式一（ws）：纯 WS 往返 —— 隔离 WS 这一腿
serial-client probe -server http://<server>:8420 -mode ws -n 200

# 模式二（full）：8 字节探针出 COM 口，经回环插头（TX-RX 短接）或真实设备回来
#   全链路 = 设备 → COM → 客户端 → WS → 服务端 echo → WS → 客户端 → COM
serial-client probe -server http://<server>:8420 -mode full -port COM3 -baud 115200
```

`-mode ws` 与 `-mode full` 之差 ≈ 两条 COM 腿的成本；后者是 issue #2 验收要的数字。
full 模式需要 `-device N` 与环境变量 `EF_USER`/`EF_PASS`（生产服务器登录）。

**真机 uboot 阶段测法与安全约束**：不插回环，直接对上电中的设备板跑 `-mode full`，
探针字节会混入控制台输入流（表现为无害的乱码行），每次探针的往返仍可测。
跑 200 次取样，记录 p50/p90/p99/max。约束：

- **先验证回显**：探针靠设备把 8 字节原样吐回来计时。console/uboot 对二进制
  控制字节未必回显——先手动敲几个字符确认控制台有本地回显（echo on）再跑；
  若设备不回显，真机数字测不出，改用「回环插头 full 数字 + ws 腿数字」分解：
  真机往返 ≈ 回环 full − 回环 ws + 真机所在网络的 ws 腿数字，并在记录里注明。
- **避开 autoboot 窗口**：带 "press any key to stop autoboot" 的板子，探针字节
  会打断启动。等系统起完、停在 shell 提示符后再跑。
- **刷写中禁跑**：recovery.sh 执行期间探针字节可能污染安装流程。
- 测完重启一次设备再进刷机流程，确保控制台状态干净。

## Go/No-Go 判定标准

- **GO**：真机 p99 < 500ms 且 max < 1s → 匹配器留在服务端（现状）
- **NO-GO**：真机 p99 ≥ 500ms 或出现 >1s 长尾 → 启动 Plan B：
  匹配器下沉客户端，服务端只下发步骤序列与汇总判定
  （协议已具备条件：步骤序列本就是 JSON 下发；改动集中在客户端新增
  匹配循环 + 服务端 expect 引擎降级为规则校验器）

## Plan B 设计要点（仅 NO-GO 时展开）

1. `pkg/protocol` 增加帧：`ExpectAssign`（服务端→客户端，步骤序列）+
   `ExpectEvent`（客户端→服务端，步骤起止/匹配/超时）
2. serial-client 增加 match 循环（复用 `server/internal/expect` 的纯逻辑包——
   该包无 IO 依赖，可直接进 `pkg/` 共享）
3. 服务端会话日志仍收全量 RX/TX（客户端逐帧上报），报告语义不变
4. 改动边界：transport 层不动；session 内核不动；UI 不动
