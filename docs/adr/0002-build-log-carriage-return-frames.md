# ADR-0002: 构建日志的回车帧收敛——每个进度流只保留最后一帧

日期: 2026-09-21
状态: 已采纳

## 背景

构建日志按行落盘（`<ts> [phase] content\n`），行切分此前只按 `\n`。git 的进度输出（clone/fetch 的 `Updating files: x% (n/m)`、`Receiving objects` 等）是**单行流**：过程用 `\r`（回车）原地刷新，只在整段结束时补一个 `\n`。结果 100 个进度帧粘成一行落盘，Web 端 `<pre>` 里 `\r` 不渲染为换行，用户看到一大坨（生产 192.168.0.80 报「log 不换行」）。

第一版修复把 `\r` 也当行分隔符，每帧一行——解决了粘行，但引入新问题：一次 clone 刷出 ~100 行零信息量的百分比帧，刷屏。

## 决策

`scannerLines`（`server/internal/builder/builder.go`）的切分规则：

1. 先按 `\n` 切块（正常行）；
2. 块内按 `\r` 切帧，**只保留最后一个非空帧**（如 `Updating files: 100% (725/725), done.`）；
3. 只去掉 `\r` 残留，保留行首空格（git 的 ` * branch ...` 行依赖前导空格，`TrimSpace` 会吃掉它）。

中间帧不落盘、不推送。git 全部输出经 `runGitLogged` 一处收口，clone/fetch/checkout 场景统一生效。

## 否决的替代方案

- **前端渲染时处理 `\r`**：日志文件本身仍存着粘行 blob，下载的 log.txt 依旧不可读；且所有消费方（Web 分段视图、tail 下载、live WS 推送）各自要处理。在写入端收敛一次，下游全部干净。
- **保留每帧一行**：信息量为零的百分比 tick 不是审计信息，刷屏代价大于价值。真正的逐帧需求（如有）未来可走 WS 实时流，不进持久日志。

## 后果

- 正向：日志紧凑且人类可读；持久日志、WS 推送、tail 下载三个消费方一致。
- 约束：构建命令自身的输出若依赖 `\r` 表达信息（极少见，如单行进度表）将只保留终帧。测试 `TestScannerLines_CarriageReturnFrames` 锁定行为（多帧收敛 + 前导空格保留）。
