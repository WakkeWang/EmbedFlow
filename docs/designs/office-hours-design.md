## Problem Statement

中小嵌入式团队（如 YY0133 产品线）的日常：构建靠裸编译服务器 + 手敲命令，刷机靠 SecureCRT + VBS 脚本，测试用例管在 Excel，测试报告手写 Word，发布靠手动拷贝。全流程割裂、无记录、无追溯，每个版本重复一遍。现有开源工具（LAVA、LabGrid、pytest-embedded、Renode）全部假设「串口在服务器上、一切可自动化」，不匹配中小团队「串口插在个人电脑 + 人机混合测试」的现实。

## What Makes This Cool

**人机混合测试作为一等公民**：人为观察（LED/蜂鸣器）和人为干预（插拔电源线）是测试流程中的正式 step，有提示词、有 Web 确认、进报告——这是与所有现有 HIL 框架的根本分叉，也是开源叙事的差异化点。

**串口透传架构**：串口留在测试人员 Windows 电脑上，exe 客户端纯透传到服务器。不买串口服务器、不改机架，装个 exe 就接入，采用门槛≈零。

**可配置 expect 刷机**：把 VBS 脚本的「等待字符串 + 发送 + 超时」三要素模型变成 Web 可配置的 expect 步骤序列，刷机规则化、可复用、全程留痕。

## Constraints

- 单台编译服务器（192.168.0.80），Go + Vue3 + SQLite，单二进制自托管
- 串口客户端 Go + Wails，纯透传无业务逻辑
- MIT + 单仓库（server/ + serial-client/ + web/），中英文双语界面
- 第一版明确不做：定时/API 触发构建、自动保留策略、通知、设备排队、用例管理系统、任意布尔依赖表达式
- 双目标同步长：内部先用起来 + 每个公开版本打磨可展示面（双语 README、截图、客户端体验）

## Premises

1. 痛点是自己的、真实的（一线嵌入式工程师日常）——同意
2. 「人机混合测试」是差异化之根，砍掉它就只是又一个 CI——同意
3. 串口客户端透传是采用门槛的解法——同意
4. 内部先用起来 + 为 star 优化，两者同步长——同意（用户修正：不只是自己先用）

**EUREKA（已记录）**：所有现有 HIL 框架在自动化方向内卷，但中小团队的真实瓶颈是人机混合流程没有数字化载体。把「人」作为流程一等公民是与 LAVA 们的根本分叉。

## Approaches Considered

### Approach A: 最小可行——单机全栈直通
严格按需求文档实现四大板块，不预设抽象。Effort: L（6-8 周业余时间）。Risk: Low。
被排除原因：开源后接外部需求要动地基，通用性欠账。

### Approach B: 理想架构——领域内核 + 执行器分层（已选定）
A 的全部功能 + 内核/执行器分层 + 四类规则统一配置对象（统一持久化与导入导出，不统一执行语义）。Effort: L+（比 A 多 1-2 周，花在内核边界设计）。Risk: Low-Med（过度设计风险，需克制）。完整论述见 Recommended Approach。

### Approach C: 横向切入——只做人机混合会话层
设备 + 串口透传 + 会话日志 + expect + 人为确认，构建靠现有 CI。Effort: S（2-3 周）。Risk: Low。
未被单独选择，但作为 B 的首个里程碑 M1 收编（先验证核心创新）。

## Recommended Approach

**Approach B: 理想架构——领域内核 + 执行器分层**（用户已选定）

- 服务端分两层：**领域内核**（数据模型 + 状态机，纯 Go 无 IO）+ **执行器层**（构建执行器、串口会话执行器、expect 引擎、SSH 执行器、报告生成器）
- 领域内核实体清单：**用户**（两级角色：管理员/成员，管理员开账号，服务端 session）+ **工程** + **设备** + **会话** + **四类配置对象**（构建项目、部署规则、测试用例单元/项/集合、发布规则）+ **运行记录**（批次、构建记录、部署记录、测试运行、发布记录、产物）。完整字段定义以 `docs/需求文档.md` 为准，此处只定内核归属
- 四类规则（构建项目、部署规则、测试用例单元/项/集合、发布规则）统一为一种「配置对象」：**持久化与 JSON 导入导出层面统一**（一套存储 + 一套导出/导入 + 一套复制粘贴），**执行语义归各执行器**（不造行为层的统一接口）。配置中心是这一统一的 Web 兑现
- expect 引擎四要素：等待字符串 + 可选发送 + 超时 + 失败动作（与 CONTEXT.md 词汇表一致）
- 里程碑：M1 = 会话层（验证核心创新）→ M2 = 构建板块 → M3 = 部署板块（SSH + 刷机）→ M4 = 测试板块 + 报告 → M5 = 发布板块。**此顺序有意调整需求文档 7.3 的 MVP 顺序**（原文为构建先行），理由：M1 最先验证差异化核心（人机混合会话层），其透传协议和 expect 引擎是后续所有板块的地基
- 开源后接新需求（新刷机方式、新测试通路）只加执行器，不动内核

### 架构决策（/plan-eng-review 2026-09-18）

| # | 决策 | 内容 |
|---|---|---|
| 1A | SSH 与会话分层建模 | 会话实体 = 串口持久会话；SSH 命令执行单独建模为「命令执行记录」（短事务，挂部署记录/测试运行下，不进会话状态机）；日志各自落盘，报告两者都引用 |
| 2A | 接受单点 | 服务器宕机 = 团队停摆，风险与编译服务器本身等价，第一版不加机制，架构说明写一行；运维说明补一句「定期拷贝数据目录（SQLite + 产物）到另一块盘」 |
| 3A | 传输层认证 | HTTP WebSocket 同源校验；客户端长连接 token 认证 |
| 4A | 透传协议 | WebSocket 双帧：控制帧 JSON（认证/心跳/共享请求/设备状态），数据帧 binary（串口字节流）；心跳、重连、浏览器兼容现成 |
| 5A | 共享代码位置 | 单仓库 `pkg/protocol/` 共享包（连接帧定义 + 日志格式），server 和 serial-client 都引用（Go workspace） |
| 6A | 内核抽取深度 | 第一版克制：只抽纯逻辑（会话状态机、批次调度状态机、expect 匹配器），其余在执行器里；M2+ 出现重复模式再提炼 |
| 7A | 测试策略 | 分层：内核表驱动单测 + SerialPort 接口抽象 + 内存管道做 CI 集成测试（不依赖 com0com 内核驱动，com0com 只留本地手测）+ 真机手动验收 |
| 8A | 日志写入 | bufio 缓冲写（定时/定量刷新）+ WS 推送 100ms 窗口聚合 + 单帧 64KB 上限截断标记 + 二进制安全转义 |
| 9A | 日志下载 | HTTP Range 分段流式（Go 标准库原生支持），浏览器断点续传免费 |
| 10A | SQLite 并发 | WAL 模式 + busy_timeout + 写操作收敛到单写协程（串行写队列），读走 WAL 并发 |
| 11A | 会话空闲超时 | 手动会话无输入超时自动关闭（默认 30 分钟，可配置），防忘关锁死设备互斥；状态机加 IDLE 超时转移 |
| 12A | 客户端重连语义 | 重连只恢复共享态（串口重新绑定），不恢复任务会话（任务会话断线即 FAILED，与需求 3.5 一致）；T4 验收标准写明 |
| 13A | token 存储 | 客户端 token 在 Windows 用 DPAPI 加密存储，不落明文文件 |
| 14A | star 轨道节奏 | star 优化只在两处用力：M1 种子（首个 README + 截图）和 v0.1.0 发布；中间 minor 版本不强制打磨演示 |
| 15A | 排期修正 | M1 估时从 3 周修正为 4-6 周（含业余时间折算：业余投入约 2-3 个月日历时间）；M2-M5 逐个里程碑开工前重估，不预先承诺日期 |
| 16A | M1 验收编辑路径 | M1 增加 expect 序列的最小编辑 UI（Web 表单编辑步骤序列，替代手写 JSON 灌库），验收走产品形态 |
| 17A | 凭据与公开脱敏 | 会话日志密码脱敏选项列 M3 实现（M1 记 TODO）；仓库公开前对 docs/ 做一次脱敏 pass（内网 IP、真实路径、产品线名），公开前执行 |

### 会话状态机（M1，决策 1A/2A 后修订）

```
                    ┌──────────────┐
        开会话请求  │    IDLE      │ 设备空闲
      ┌────────────┤  (设备空闲)   ├────────────┐
      │            └──────┬───────┘            │
      │ 占用成功          │ 忙时拒绝            │
      │                   ▼                    │
┌─────┴──────┐     ┌──────────────┐
│   TASK     │     │   MANUAL     │  两类会话
│ (任务会话)  │     │  (手动会话)   │
├────────────┤     ├──────────────┤
│ 断线→FAILED│     │ 断线→CLOSED  │
│ 日志标中断  │     │ 释放互斥     │
│ 互斥释放    │     │ 重连需新开会话│
└─────┬──────┘     └──────┬───────┘
      │ 完成/失败/取消     │ 用户关闭
      ▼                   ▼
┌─────────────────────────────┐
│  CLOSED / FAILED → 回 IDLE  │
└─────────────────────────────┘
```

## Failure modes（M1 新代码路径的失败场景）

| 代码路径 | 生产失败场景 | 有测试? | 有错误处理? | 用户可见性 |
|---|---|---|---|---|
| 会话互斥 | 双人同时开会话竞态 | 是（内核单测并发用例） | 是（忙拒绝） | 清晰提示「设备忙」 |
| 任务会话断线 | 客户端崩溃/拔线 | 是（单测 + 集成） | 是（失败终止+日志标注） | 任务页显示失败原因 |
| 手动会话断线 | 网络闪断 | 是（单测） | 是（释放互斥） | 终端页显示断开 |
| expect 匹配 | 设备输出比预期慢 | 是（表驱动含超时分支） | 是（超时→配置的失败动作） | 实时日志可见 |
| WS 双帧解析 | 客户端发畸形帧 | 是（协议单测） | 是（断开连接+日志） | 客户端重连 |
| 日志落盘 | 磁盘满 | **否** | 待定 | **可能静默失败** ⚠️ |
| 客户端 COM 异常 | 串口被其他程序抢占 | 是（集成测试） | 是（上报+状态显示） | 客户端 GUI 提示 |

**关键缺口（磁盘满场景）**：磁盘满时日志写失败如果静默吞掉，刷机记录不完整且无人知道。修复要求：写失败 = 会话标记「日志不完整」警告 + WS 推送给操作员。此修复已纳入 M1 任务（见 Implementation Tasks T2）。
